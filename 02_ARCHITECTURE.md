# Архитектура MusicRadio

Документ для того, кто будет это сопровождать: почему три мода, как летят
пакеты, где хранится правда и что произойдёт, если выключить свет.

## 1. Разделение на три мода

```
             ┌────────────────────────────┐
             │  @MusicRadioServer (мод 1) │  только сервер
             │  права, лимиты, аудит      │  MR_ServerEngine
             └────────────┬───────────────┘
                          │ RPC (строки, MR.RPC_*)
             ┌────────────┴───────────────┐
             │  @MusicRadioCore  (мод 2)  │  сервер + клиент
             │  протокол, библиотека, UI  │  MR_Net / MR_Library / MR_RadioMenu
             └────────────┬───────────────┘
                          │ locator + SoundSet
             ┌────────────┴───────────────┐
             │  @MusicRadioDB    (мод 3)  │  сервер + клиент
             │  .ogg + CfgSoundSets       │  контент, без логики
             └────────────────────────────┘
```

Правила, которые нельзя нарушать:

1. **Мод 3 не содержит кода.** Только файлы и `config.cpp`. Тогда обновление
   музыки никогда не требует обновления логики.
2. **Мод 2 не знает путей к файлам.** Он знает только: `provider` + `trackId` →
   имя SoundSet по формуле. Это единственный контракт между модом 2 и модом 3.
3. **Мод 1 не знает про звук.** Он решает «можно/нельзя» и «кто это услышит».
   Звук включают клиенты.
4. Стрелки зависимостей идут только вниз. `3_Game` никогда не ссылается на
   `4_World`/`5_Mission` (это проверяет `tools/check_project.py`).

## 2. Слои скриптов

| Слой | Что там | Почему именно там |
|------|---------|-------------------|
| `3_Game` | `MR`, `MR_Locator`, `MR_Json`, `MR_Track`, `MR_Library`, `MR_Net`, `MR_MediaResolver`, `MR_DeviceBase`, `MR_AudioTypes` | должно быть доступно везде, включая меню-миссию |
| `4_World` | `MR_Registry`, `MR_Hosts` (item/vehicle), `modded CarScript/PersonalRadio/PlayerBase` | нужны классы мира (`CarScript`, `PlayerBase`) |
| `5_Mission` | `MR_ClientRPC`, `MR_RadioMenu`, `MR_GameHooks`, и весь серверный мод | нужен `MissionGameplay` / `MissionServer` |

## 3. Контракт «трек → звук»

Сервер **никогда** не отправляет клиенту путь к файлу. Он отправляет локатор:

```
LCT|1|MusicRadioDB|wasteland_01|6|48311
     │  │            │          │ └ seed (для слотов потоков)
     │  │            │          └ громкость 0..10
     │  │            └ trackId
     │  └ provider (какой медиа-пак)
     └ версия протокола
```

Клиент по локатору находит трек в своей копии пака и строит имя SoundSet:

```
MR_ + normalize(provider) + _ + normalize(trackId) + _SoundSet
MR_MUSICRADIODB_WASTELAND_01_SoundSet
```

Затем **проверяет** его через `GetGame().ConfigIsExisting("CfgSoundSets ...")`.
Если SoundSet нет — трек серый с подписью «pack missing», музыка не начнётся, в
чат придёт понятное сообщение. Никаких «тихих» отказов.

Плюсы схемы:

* переименование папки пака не ломает сервер;
* сервер не должен содержать копию музыки (это десятки гигабайт);
* клиент физически не может проиграть трек, которого у него нет.

## 4. Путь одного нажатия «PLAY»

```
UI (MR_RadioMenu)
  └─ MR_ClientRPC.RequestPlay(host, type, ids, trackId, kind)
       └─ ScriptRPC "action=1|type|idLow|idHigh|trackId|vol|radius|broadcast"
            └─ SERVER  MR_ServerEngine.HandleRequest
                 ├─ флаги функций (vehicleRadio / internetRadio / localTracks)
                 ├─ кулдаун (limits.cooldownSeconds)
                 ├─ трек существует и enabled
                 ├─ объект-хост существует и в 6 м от игрока
                 ├─ правила хоста: рация не ruined, батарейка, игрок в машине
                 ├─ сессия в таблицу m_Sessions (одна на хост)
                 └─ DispatchPlay → RPC_PLAY всем в радиусе
                                  → RPC_REPLY инициатору
                                  → RPC_NOWPLAYING всем (титр в чат)
  └─ КЛИЕНТЫ  MR_ClientRPC.HandlePlay
       ├─ находят трек в локальной библиотеке
       ├─ резолвят SoundSet (с проверкой)
       ├─ host.MR_AudioStart(soundSet, loop, offset)
       └─ MR_ClientAudio.Register → каждый тик пересчитывает громкость
```

Клиент не решает «можно ли». Взломанный клиент может максимум надоесть сам
себе: сервер просто не пришлёт `RPC_PLAY` остальным.

## 5. Громкость и затухание

* Пользовательская громкость: шаг 0..10 → `gain = (step/10)^1.6` (восприятие,
  а не линейно).
* Затухание по расстоянию (`MR.DistanceGain`):
  * 0–35 % радиуса — полная громкость;
  * 35–100 % — плавное падение до нуля (`1 - t²`);
  * дальше радиуса — не слышно (сервер вообще не присылает PLAY таким клиентам).
* Итог: `SetSoundVolume(userGain * distanceGain)`, пересчёт каждые 250 мс в
  `MR_ClientAudio.Tick`, с защитой от лишних вызовов (изменилось < 1 % — не
  трогаем).

## 6. Синхронизация и опоздавшие

Сессия на сервере хранит `m_StartTimeMs` и `m_StartOffset`. Клиент, зашедший
позже (или вошедший в радиус), получает `RPC_PLAY` с `startOffset =
CurrentOffset()` и продолжает с той же секунды.

Конец трека определяет **клиент** (у него аудио-часы) и присылает
`ACT_NEXT`; сервер выбирает следующий трек и рассылает `RPC_PLAY`. На случай,
если все клиенты отвалились, в `MR_ServerEngine.Tick` есть страховка:
сессия старше `duration + 5 c` закрывается.

Сессии живут в памяти и **не переживают рестарт сервера** — это осознанно:
иначе после падения сервера машины на карте «пели» бы вечно.

## 7. Watchdog (раз в секунду)

`MR_ServerEngine.Tick`:

* `MR_Registry.Prune()` — выбросить исчезнувшие объекты;
* хост существует? машина не ruined? рация в грузе всё ещё на месте и с
  батарейкой? — иначе `RPC_STOP` с причиной.

Причины остановки (`MR_StopReason`) доходят до клиента — игрок видит не
«музыка пропала», а «radio destroyed» / «radio out of range».

## 8. Сеть

| RPC | Направление | Полезная нагрузка |
|-----|-------------|-------------------|
| `RPC_REQUEST` 784107 | клиент → сервер | запрос (действие, хост, трек, громкость) |
| `RPC_REPLY` 784108 | сервер → клиент | ok/нет + текст ошибки |
| `RPC_CONFIG` 784101 | сервер → клиент | JSON настроек |
| `RPC_LIBRARY` 784102 | сервер → клиент | манифест треков |
| `RPC_PLAY` 784103 | сервер → клиенты в радиусе | локатор + параметры |
| `RPC_STOP` 784104 | сервер → клиенты | причина |
| `RPC_VOLUME` 784105 | сервер → клиенты | новая громкость |
| `RPC_NOWPLAYING` 784109 | сервер → все | «исполнитель — трек» |

Почему строки, а не `Param3<...>`: их видно в логах, неизвестные хвостовые поля
игнорируются (совместимость вперёд), и не надо согласовывать типы между модами.
Всё, что попадает в строку, проходит `MR_Net.Sanitize` (убирает `\n`/`\t`), так
что подделать структуру через название трека нельзя.

### Кто где принимает RPC

| Направление | transport | приёмник |
|-------------|-----------|----------|
| клиент → сервер (запросы) | `rpc.Send(player, RPC_REQUEST, true, null)` | `modded PlayerBase.OnRPC` (только в `@MusicRadioServer`) |
| сервер → клиент (всё остальное) | `rpc.Send(null, RPC_*, true, identity)` | `modded DayZGame.OnRPC` (только в `@MusicRadioCore`) |

Это разделение сделано намеренно: **два мода никогда не переопределяют один и
тот же метод движка**. Если бы и Core, и Server патчили `DayZGame.OnRPC` на
сервере, порядок `super.OnRPC` зависел бы от того, какой мод загрузился первым —
классический источник «у одних работает, у других нет».

`Send()` не очищает буфер — на каждый пакет создаётся новый `ScriptRPC`
(`Send()` не сбрасывает данные, `Reset()` в новых сборках может отсутствовать).

## 10. Совместимость и производительность

* Патчатся только `PersonalRadio`, `CarScript`, `PlayerBase`, `MissionGameplay`,
  `MissionServer`, `DayZGame` — и только добавлением членов/методов, без
  переопределения ванильного поведения (кроме `EEKilled`/`EEDelete`, где мы
  вызываем `super`).
* Никаких `while`/`Sleep` в скриптах: всё через `CallQueue` (250 мс клиент,
  1000 мс сервер).
* `MR_Json` — толерантный парсер (комментарии, `#`, одинарные кавычки,
  висячие запятые): базу можно вести руками, не боясь сломать загрузку.
* Библиотека читается один раз при старте; сервер отдаёт клиенту компактный
  манифест (`id/provider/kind/title/artist/duration/kind`, для потоков ещё `url`).

## 11. Ограничения, о которых надо помнить

1. **Нет прямого проигрывания URL** — см. `docs/03_INTERNET_RADIO.md`.
2. `IsAdmin()` по умолчанию `false`: в DayZ нет переносимого «я админ» для
   скрипта. Если у вас есть мод прав — расширьте одну функцию
   `MR_ServerEngine.IsAdmin`.
3. `NetworkIDHigh` может отличаться между сервером и клиентом на некоторых
   сборках — поэтому в реестре есть `FindLoose()` по низкому id.
4. Громкость `SetSoundVolume` относительная; абсолютный уровень всё равно
   ограничен настройками звука игрока (как и должно быть).
